# 変更プレビュー・選択・インデント・数量推奨（Issue #23・#24・#25）

[目次](../README.md) / [前回の Engine 調査と数量 ADD](focused-cpu-and-quantity-counters.md)

## 調査した問題

| Issue | 既存コードの原因 | 変更 |
| --- | --- | --- |
| #23 | 付与後の全文を TextBox に表示しており、追加位置と変更ブロックを示していなかった | 両画面共通の色付きプレビューと前後移動 |
| #24 | 関数・分岐への挿入とカウンター宣言で `\t` を固定追加していた | ローカルの文のインデントを優先して検出 |
| #25 | CPU は解析直後にプレビュー、イベントは解析とプレビューが別操作。CPU は全変更ファイルへ適用していた | 共通の画面配置、解析時の自動プレビュー、一覧での適用選択、検索 |
| #25 数量 | 安全な値引数の候補 `AddValues` は出していたが、値・単位を利用者が毎回入力していた | 型と識別子から限定的に推奨し、未確認の変更案へ表示 |

数量の意味は前回調査した Engine の実例を再確認しました。`Engine/Source/Developer/DerivedDataCache/Private/HttpCacheStore.cpp:2771–2772` は物理送受信サイズ、3156・3179行付近は `Requests.Num()` によるバッチ件数です。実処理量・要求量・容量の区別やメンバー式の副作用を型・名前だけでは判定できません。このため推奨を意味の確定とは扱いません。

## 両画面の操作

1. Source フォルダーを指定し「解析・プレビュー」。左に対象一覧、右に付与後・付与前等のタブを表示します。
2. 検索でパス・関数名等を絞り、行をクリックしてそのファイルの変更案を確認します。
3. 一覧の「適用」をチェック。CPU はファイル単位、イベントは分岐候補単位です。初期選択は両方0件です。
4. 選択した変更案をレポート保存、またはバックアップ付きで元ファイルへ適用します。

「表示中を選択」「表示中を解除」は検索結果だけに作用します。隠れた選択は維持し、適用対象にも残します。CPU の適用時は選択したファイルだけで計画を作り、未選択ファイルへの書き込み・バックアップはしません。ファイル全体の変更案が対象なので、CPU の関数単位選択はありません。

イベントは選択0件の間、全候補を含む参考プレビューを出します。適用・保存は無効です。1件以上選ぶとその選択だけでプレビューを再構築します。名前・数量・選択の変更直後に旧計画を無効化し、入力が300ms止まったら更新します。「プレビューを更新」でも即時更新できます。入力途中のエラーはステータスへ表示し、ダイアログで編集を中断しません。

CPU の検索文字は `CpuTracing.Filter` に保存します。イベントの検索・カウンター名の保存は継続します。適用の選択や確認状態は保存しません。ソースパスや CPU 対象モードを変えると計画を破棄します。

## 変更行と移動

`UEEtc.Wpf.Preview.CodeChangePreview` を両画面で使用します。行番号を表示し、変更行は緑色の背景と `+` を付け、連続した変更行を一つの変更箇所として数えます。「次の変更」「前の変更」で実際の文書をスクロールし、最後・先頭から循環します。ファイル切替時は移動位置をリセットします。

共通コアの `ChangedLineMap` は前後の共通行と一意な行の順序をアンカーにします。行数の二乗の比較表を作りません。現行ツールの追加中心の差分をレビューするための表示で、C++ の意味解析ではありません。一行の関数を複数行に分けた場合や曖昧な繰り返し行付近では、元からある文字を含む変更行全体を着色します。元ソースの色や改行を書き換える機能ではありません。

## インデント

`UEEtc.Core.Source.SourceIndentation` を CPU・進入回数・イベント・数量で共用します。

- 挿入ブロックの直接の文に行頭インデントがあれば、その文字列をそのまま使います。ローカルで混在したタブとスペースも維持します。
- 新設する匿名名前空間の宣言等では、既存の `{` の次の文への字下げを数え、最も多い単位を使います。引数の継続行の整列幅を優先しません。
- 明確なブロック例がない場合はファイル内の行頭から推定し、手掛かりが全くなければ従来互換のタブを使います。
- 既存の文のインデントは直しません。改行・文字コード・BOM の保持は従来どおりです。

2スペース、4スペース、タブ、混在、入れ子、継続行、CRLF のテストを追加しました。独自フォーマッターの規則や意図的な不規則インデントを完全には復元しません。

## 数量 ADD の推奨

`EventCounterCandidate.RecommendedQuantity` に値・単位・理由を追加しました。既存の `AddValues` に含まれる安全な値引数だけが対象です。

| 識別子の例 | 推奨単位 |
| --- | --- |
| NumBytes / ByteCount / Bytes / BytesWritten / BytesRead / WrittenBytes / ReadBytes | bytes |
| NumItems / ItemCount / NumElements / ElementCount | items |

大文字小文字、アンダースコア、先頭の `In` は正規化します。複数の推奨候補がある場合は選びません。`Size` のように単位が曖昧な名前、符号付き・64ビット・参照、挿入前に使われた引数、メンバー参照や関数呼び出しは推奨しません。

WPF は推奨を新規解析ごとに「名前・数量ADD」へ入力し、ADD 有効・意味未確認の参考プレビューを作ります。利用者は意味・単位を確認するか、ADD を無効にして回数だけを選べます。値・単位を編集すると確認を解除します。数量の手入力や確認状態は復元しません。

Core の `BuildPreview` は未確認数量を表示用に生成できますが、`RequiresQuantityConfirmation=true` を付けます。共通の `SourceWorkspace.Apply` 自体がこの計画を拒否するため、画面のボタンを通さずに適用することもできません。従来の `BuildPlan` と CLI の選択 JSON は未確認数量を引き続き拒否します。CLI の discovery JSON に推奨を追加しましたが、空の初期選択は維持しています。

## 検証と限界

- Core 94/94、WPF 81チェック。変更色、実スクロール、循環移動、検索と隠れた選択、選択した1ファイルだけの適用とバックアップ、自動プレビュー、数量推奨・確認・無効な入力を確認。
- Release ビルドは警告0・エラー0。MSVC `/W4 /WX` は既存12構成、CPU配置4構成、数量併用2構成で有効・無効時の動作を確認。
- Lyra はイベント1525候補、BlockBreaker は423候補。全候補をコピーに付ける構文上の負荷検証であり、有用な全候補の推奨ではありません。差分適用確認が通り、コピー再解析の候補は0。
- CPU の追加候補は451／93のまま。コピー再解析の追加変更0、診断0。両実験とも元599ファイルの SHA-256 は一致。
- 数量推奨は両プロジェクトとも0件。Lyra の安全な値引数候補2件は `ALyraCharacter::SetMovementModeTag` の `CustomMovementMode` で、数量ではないため推奨しません。BlockBreaker の安全な値引数候補は0件です。
- NumBytes を持つ検証用 C++ ソースでは、推奨ADDのプレビュー、未確認時の適用拒否、確認後の有効化、インデント維持を確認しました。実プロジェクトに存在しない数量を補っていません。

Engine／ゲーム元ソースへの適用、UE全体のビルド、Insights による実測は行っていません。Issue #10 の有用なイベント候補抽出そのものは継続課題です。
